# Hackathon PO : un daily qui sert

## Le problème
Les sprints ont rarement un objectif commun, chacun avance sur son sujet, et le daily tourne au tour de table. Il devrait servir à une chose : **vérifier que l'engagement pris au sprint planning tient toujours**, et traiter les frictions du flux.

## Votre agent
Lancé avant le daily, il lit le sprint en cours dans Jira et lève toutes les alertes : ce qui est bloqué, ce qu'il faut terminer avant de commencer autre chose, les synchros à organiser, ce qui est gros et pas commencé. Il vous donne l'ordre du jour d'un daily efficace.

## Ce que vous lui donnez
- Le connecteur **Jira** (précisez la clé de votre projet, ex. « projet Jira DI »)
- Votre workspace **Contexte**
- La fiche **daily-efficace** dans votre workspace **Expertise**

## Votre agent est un produit
- Un problème, un livrable. Petit d'abord : un premier agent qui marche vaut mieux qu'un agent complet qui ne tourne pas.
- On itère : lundi, vous le relancez et vous l'améliorez.

## Les 45 minutes
| | |
|---|---|
| **5 min** | Le livrable : dessinez sur papier l'écran que vous voulez lire avant le daily |
| **15 min** | Le workflow à la main : faites-le une fois dans une conversation, sur votre vrai sprint, jusqu'à obtenir le bon livrable |
| **15 min** | L'agent : transformez ce qui a marché en instructions d'agent, relancez dans une nouvelle conversation |
| **10 min** | La version de lundi : corrigez une chose, une seule |

## Restitution, 2 minutes
Le livrable produit sur votre sprint, ce qui a marché, ce que vous ferez ensuite.

## Pièges
- Jira charge beaucoup d'outils et consomme le quota : cochez-le seul, ouvrez une nouvelle conversation à chaque essai.
- Pas de pourcentage de réussite ni de date calculée : l'agent compte, il ne prédit pas.
